# rag/ — 政府工作报告向量检索原型

把 `md/` 下 27 份国务院政府工作报告（2000–2026）切块、嵌入、存入 LanceDB，并支持语义检索。

## 快速开始

```bash
# 1. 环境（已建好，重装时用）
uv venv --python 3.13 .venv
VIRTUAL_ENV=.venv uv pip install -r rag/requirements.txt

# 2. 建库（首次会从 hf-mirror.com 下载模型；--device mps 约快 1.7 倍）
./.venv/bin/python rag/build_db.py --rebuild --device mps

# 3. 检索
./.venv/bin/python rag/search.py "新能源汽车产量" -k 5
./.venv/bin/python rag/search.py "减税降费" --year-from 2020
./.venv/bin/python rag/search.py "乡村振兴" --section 工作回顾
./.venv/bin/python rag/search.py -i          # 交互模式
./.venv/bin/python rag/search.py "碳达峰" --json
```

## 为什么不建向量索引

**这是刻意的设计，不是遗漏。** 建库脚本里没有 `create_index()` 调用。

本语料 1428 块，LanceDB 走暴力精确检索：**召回率 100%，p50 约 3ms**。加 IVF_PQ 这类 ANN 索引只会引入有损量化（PQ 压缩），在这个量级收益接近于零。

索引应当由**规模**驱动，而不是预先加上。实测参考（M4 / 24GB）：

| 规模 | 索引 | 稳态内存 | 查询 p50 |
| --- | --- | --- | --- |
| 1110 × 1024 | 无 | 201 MB | 2.51 ms |
| 1110 × 1024 | IVF_PQ | 240 MB | 1.82 ms |
| 10万 × 768 | 无 | 923 MB | 39.3 ms |
| 20万 × 768 | IVF_PQ | 143 MB | 3.3 ms |

注意一个反直觉现象：**无索引时全量向量必须常驻内存**（10 万条约 0.9GB），而 IVF_PQ 走磁盘 + 量化压缩，常驻反而只有 143MB。所以省内存的其实是索引。按此斜率，无索引方案到百万级约需 10GB 内存——**那时才必须建索引**。

`build_db.py` 里的 `INDEX_THRESHOLD = 50_000` 是个提示阈值：超过它会打印建索引的建议命令。本语料离得很远。

> 另一处代价：IVF_PQ 索引构建是纯 CPU，实测 20 万 × 768 在 M4 上耗时 **100 秒**。真到百万级需要把构建耗时纳入运维考虑。

## 文件

| 文件 | 作用 |
| --- | --- |
| `corpus.py` | 解析 md、按 `##` 分节、段落贪心装箱切块（450 字目标 / 80 字重叠） |
| `embedder.py` | 模型登记表与嵌入封装 |
| `build_db.py` | 切块 → 嵌入 → 写入 LanceDB（**不建索引**） |
| `search.py` | 检索 CLI，支持 `-k` / 年份区间 / 章节过滤 / JSON 输出 |
| `db/<模型名>/` | LanceDB 数据目录，每个模型一份 |

## 切块策略

面向中文公文，不是通用等长切分：

1. 按 `## 一、xxx` 分节，记录所属章节
2. 元信息表、标题行、分隔线全部剔除（不进入向量）
3. 段落贪心装箱到 450 字左右；单段超 700 字则先按 `。！？；` 切句
4. 块间保留 80 字重叠，避免跨块语义被切断
5. 过短碎片（<120 字，如只有「各位代表：」）并入相邻块
6. **嵌入文本带章节前缀**：`{year}年国务院政府工作报告 · {section}\n{正文}`，显著改善「哪一年的哪项工作」类查询
7. 存档的 `text` 字段不含前缀，仅供展示

## 嵌入的两个坑

**1. BGE 中文系列的查询指令前缀。** `bge-*-zh-v1.5` 在检索任务上要求给 **query** 加前缀 `为这个句子生成表示以用于检索相关文章：`，文档侧不加。漏掉会明显掉召回。已按模型在 `embedder.py` 里分派（`bge-m3` 不需要前缀）。

**2. HuggingFace 直连不通。** 本机 `huggingface.co` 超时（HTTP 000），`hf-mirror.com` 正常。`embedder.py` 在 import transformers **之前**设了 `HF_ENDPOINT`，这一点必须在导入顺序上保证。

## 模型选择：实测下来 bge-large 不值得

默认 `bge-small-zh-v1.5`。**不是图省事，是实测对比后 large 没有稳定胜出。**

成本差得很悬殊（M4 实测，1428 块）：

| 模型 | 维度 | 体积 | 建库吞吐(CPU) | 建库吞吐(MPS) | 全量建库耗时(MPS) |
| --- | --- | --- | --- | --- | --- |
| `bge-small-zh-v1.5` | 512 | ~95 MB | 68 块/秒 | 112 块/秒 | ~13 秒 |
| `bge-large-zh-v1.5` | 1024 | ~1.3 GB | **3.5 块/秒** | 6.5 块/秒 | ~3.7 分钟 |

**14 倍体积、20 倍耗时，质量却是互有胜负：**

| 查询 | small (512d) top-1 | large (1024d) top-1 |
| --- | --- | --- |
| 新能源汽车产量 | ✅ 2026 — 「新能源汽车年产量超过1600万辆」直接给数字 | ❌ 2024 — 「巩固扩大智能网联新能源汽车等产业领先优势」，无产量数字 |
| 粮食安全 耕地红线 | ❌ 2001 — 粮食流通体制改革，未及耕地 | ✅ 2021 — 「保障粮食安全的要害是种子和耕地…坚决遏制耕地非农化」 |

**结论：这个量级上，换更大的向量模型不是提升精度的有效杠杆。** 真正的杠杆是 **cross-encoder 重排** 和 **BM25 混合检索**（见下）。

> 上表的 large 结果来自一次性对比实验，**其模型缓存和向量库已按"确定不用"清理掉**（省 5.3 GB）。要复现需重新 `--model bge-large-zh-v1.5 --rebuild`，会重新下载 1.3 GB 权重、MPS 下约 3.7 分钟。

其他可选项（同样只改 `--model`，各模型在 `db/` 下独立成库）：

| 模型 | 维度 | 体积 | 说明 |
| --- | --- | --- | --- |
| `bge-base-zh-v1.5` | 768 | ~400 MB | 中间档，未实测 |
| `bge-m3` | 1024 | ~2.2 GB | 多语言，无需查询前缀 |

### 一个坑：MPS 只是快，不是万能

`--device mps` 在**真实块长下**才占优，短文本下反而更慢（短文本实测 CPU 1938 块/秒 vs MPS 1606 块/秒；449 字真实块长下 MPS 112 vs CPU 68）。原因是大模型的收益来自长序列的矩阵运算，短序列时 MPS 的调度开销占主导。

另外注意：MPS 的 GPU 时间**不计入 CPU 占用**，所以用 `ps` 看一个正在跑 MPS 的进程会显得「几乎空闲」——不要据此误判进程卡死。判断依据应是句向量吞吐或输出文件增长。

## 已知限制

- **无重排（rerank）**。纯向量召回，跨年份的近似表述可能漂移（例：查「新能源汽车产量」，small 的第 2、3 位返回的是节能减排段落）。要提升精度，下一步是加 cross-encoder 重排，而不是换更大的向量模型。
- **无 BM25 混合检索**。专有名词、数字、年份这类精确匹配，关键词检索仍强于纯向量。
- **切块不跨年**，同一块内不会混入两年内容。
- 建库是**全量重建**（`--rebuild`），暂不支持增量追加。
- 退出时 torch 的 `loky` 信号量偶发拖住进程（`resource_tracker: leaked semaphore`），**不影响结果**，库中数据完整；脚本末尾可用 `os._exit(0)` 规避。
